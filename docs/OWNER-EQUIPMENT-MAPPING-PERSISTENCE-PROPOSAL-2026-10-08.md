# Separate equipment persistence candidate, October 8

This is an unapplied design proposal. No SQL, route, DTO, role, grant, Auth setting or connection is installed. The exported backend codec and mapper are structural candidates only. A supplied correspondence object is never evidence of a verified account or a server save. The app wrapper separately consumes an issued current owner lifetime capture after actual local write/readback acknowledgement. That LOCAL acknowledgement is not a cloud receipt.

The new canonical family is wd-owner-equipment-profile, version1, with registry917a703327aef561278fd1cd6d12580d2789ec7c01893395b9e538ad67562678, owner, planningRevision, profileRevision and equipment. Missing old adjunct remains unknown without writes. Explicit null means unanswered/unknown; [] means acknowledged known-none. The frozen30 IDs and registry order are exact. Profile revisions are safe integers at least1; planning revisions are safe integers at least0. Current v2 has exact answers/draft/week/checks and cannot losslessly persist this adjunct. Neither old reader accepts the new family, and no ninth Answer key is added.

A separately reviewed future database implementation would need a distinct WiseDinner-owned profile row, not an alteration to old v2 payloads/receipts. Proposed columns correspond exactly to canonical family/version/registry/owner/plan revision/profile revision/equipment and retained canonical bytes. Owner must reference the current active WiseDinner account; unique owner/profile identity, exact registry/version, bounded safe-integer revisions and a bounded canonical representation must be enforced. SQL arrays/JSON must preserve null versus empty, exact vocabulary/order and uniqueness, never silently coerce missing to all tools. PostgreSQL JSONB alone discards duplicate keys and is insufficient as the original byte validator: retain validated canonical bytes or validate before conversion. No live table names or grants are asserted as installed.

Read/save must run with the existing verified account and a least-privilege owned transaction, current account status/environment/eligibility and current planning revision, with default-off binding. A request owner field cannot select another owner. Equipment is not an access or canonical food replay grant. Compare-and-swap must bind the previous profile revision and exact planning correspondence. The same idempotency command with changed canonical bytes refuses; an unknown outcome retains the exact key/body/revisions and is never automatically replayed. A future receipt must reflect the stored canonical adjunct and both revisions, and must be durably acknowledged before it changes client authority. A separately reviewed atomic plan/profile operation or explicit recoverable journal is required for cloud changes spanning both records. Two unrelated remote/local writes are not atomic.

Deletion/tombstones/revocation must close admission independently of retained profile bytes. Cleanup, foreign keys, RLS, ownership, role membership, triggers, effective ACL, shared consumers, retention and backup/rollback need exact target inventory and security review before any migration. Do not reuse service_role/admin as the login, broaden anon/authenticated, touch ce_ or engine objects, or apply migrations0015/0016/0017 through this proposal. Current physical target remains unavailable/unverified.

Future review must bind both committed codecs/mappers and identical vectors, specify the exact isolated disposable target and shared consumers, inventory current schema/role/Auth usage and effective privileges, preserve reversible before-state and backup, then test owner isolation, current plan/profile CAS, concurrent connections, unknown acknowledgements, exact retry, inactive/tombstone, RLS and rollback. Credential/security-sensitive grants or actual external effects require their separate action-time gates. This document authorizes none of them.

Rollback now is to withhold the candidate binding and revert only the owned candidate source in a successor. Retain the separate local adjunct; old plan readers continue unchanged. Actual UI capture/native storage/hosted persistence/shared activation are UNRUN. The47 legacy IDs still do not join83 prepared recipe IDs; equipment mapping does not accept food/source/nutrient/package/yield/cost/allergy/cooking facts, remove raw negative nutrition/quantity/pork holds, price optional seasoning, solve or reroll.
